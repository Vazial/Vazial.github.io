Boundaries a test can enforce

A meeting-room booking system, worked from EventStorming through aggregate boundaries and concurrency control into a running Java service. It was built to practise the procedure, and it is not built out and not operated. What it demonstrates is engineering practice, and those claims do not need a product behind them — they need tests, which is the point of the whole thing.

Cancellation is a fact, not a status

The first real modelling decision. A reservation that has been cancelled is not in a "cancelled state" that someone set — something happened at a point in time, and the state is what you conclude from it.

So the only thing stored is cancelledAt. The status is derived, and the derivation lives in exactly one place:

java /** cancelledAt の有無から状態を導出する唯一の場所。 */ public static ReservationStatus of(LocalDateTime cancelledAt) { return cancelledAt == null ? CONFIRMED : CANCELLED; }

The class documentation carries the rule that matters more than the code: no other class may decide "is this cancelled" by looking at cancelledAt itself. Two sources of truth for the same question is how state models rot — one caller checks the timestamp, another checks the enum, and eventually they disagree.

The layer boundary is enforced, not agreed

Hexagonal layering is easy to draw and easy to violate. Someone needs a repository inside a domain object, adds one import, and the diagram quietly stops being true.

So the direction is a test. ArchitectureTest fails the build if the domain learns about the framework:

java noClasses().that().resideInAPackage("reservation.domain..") .should().dependOnClassesThat().resideInAnyPackage( "reservation.application..", "reservation.adapter..", "org.springframework..", "jakarta..", "javax..");

The domain package currently holds zero Spring or JPA imports, and it stays that way because breaking it turns the build red rather than requiring someone to notice it in review. Two further rules pin application away from adapter and assert the layer order in one direction only.

The rule I am most glad I wrote

Acceptance tests need a seam into the running system — something to set the clock, or plant fixtures. That seam is a back door, and back doors ship.

java classes().that().haveSimpleNameStartingWith("TestSupport") .should().beAnnotatedWith(Profile.class)

Any test-support class must be gated behind a Spring profile. It is three lines, and it removes an entire category of "how did that endpoint get into production".

The last line of defence is the database

Double booking is a concurrency problem, and an application-layer check does not solve it — two requests can both pass the check before either writes. The real guarantee is a PostgreSQL EXCLUDE constraint on the room and time range.

The interesting part is how it is verified. The test deliberately bypasses the application check and writes straight through the repository port, so that what is being proven is the constraint on its own:

L3 (DB boundary): the final defence against double booking — verifying the PostgreSQL EXCLUDE constraint. Saves directly to the port without passing the application-layer pre-check, and confirms the database alone rejects it.

It runs against a real PostgreSQL in Testcontainers, not an in-memory substitute. An H2 stand-in would have happily accepted the overlap and the test would have passed while the guarantee did not exist. Adjacent bookings that merely touch at the boundary are asserted to be allowed, which is where off-by-one errors in time ranges live.

Contracts before implementation

The OpenAPI document is the source of truth, not a description written afterwards. On the frontend side the API types are generated from it, so the client cannot drift from the contract without the build noticing.

Acceptance scenarios can also land on the main branch before the code that satisfies them, tagged @pending-implementation and excluded from the default run. That sounds minor and is not: it means "what correct means" can be agreed and merged as its own reviewable change, instead of arriving fused to an implementation that already assumes the answer.

The acceptance suite lives in its own Gradle source set with a DSL layer between the step definitions and the assertions, so the scenarios read as domain language rather than as HTTP calls.

What this does not show

It is a study exercise, so the honest limits are worth stating.

There is no deployment, no authentication, no load beyond what the tests generate, and no operational history — nothing here has been maintained under real usage or changed under pressure from real users. The concurrency guarantee is proven at the database level but has never met genuine contention.

What I take from it is narrower than "I can build a booking system", and more useful: a boundary that a test enforces stays true, and a boundary that only a diagram describes does not.
