テストが守れる境界

会議室予約システムを、EventStorming から集約境界・並行制御を経て動くJavaのサービスまで通しました。 手順を練習するために作ったもので、作り込んでおらず運用もしていません。 ここで示せるのは技術実践であり、その主張に製品は要りません——要るのはテストで、 それがこの話の全部です。

ソース · Javaファイル89本 · ADR 8本 · Gherkinの受け入れシナリオ

キャンセルは状態ではなく事実

最初の本格的なモデリング判断です。キャンセルされた予約は、誰かがセットした「キャンセル状態」に あるのではありません。ある時点で何かが起きたのであって、状態はそこから導く結論です。

だから保存するのは cancelledAt だけ。状態は導出し、導出は1箇所にしか置きません。

java /** cancelledAt の有無から状態を導出する唯一の場所。 */ public static ReservationStatus of(LocalDateTime cancelledAt) { return cancelledAt == null ? CONFIRMED : CANCELLED; }

コードより重要なのはクラスのドキュメントに書いた規則です—— 他のどのクラスも cancelledAt を直接見て「キャンセル済みか」を判定してはならない。

同じ問いに真実の源が2つあると、状態モデルはそこから腐ります。ある呼び出し側はタイムスタンプを見て、 別の側は列挙を見て、いずれ食い違う。

層の境界は「合意」ではなく「強制」する

ヘキサゴナルの層は、描くのは簡単で破るのも簡単です。誰かがドメインオブジェクトの中に リポジトリを必要として、importを1行足す。それで図は静かに真実でなくなります。

だから方向をテストにしました。ArchitectureTest は、ドメインがフレームワークを 知った時点でビルドを落とします。

java noClasses().that().resideInAPackage("reservation.domain..") .should().dependOnClassesThat().resideInAnyPackage( "reservation.application..", "reservation.adapter..", "org.springframework..", "jakarta..", "javax..");

ドメインパッケージは現在 Spring も JPA も1つもimportしていません。そしてその状態が保たれるのは、 破るとレビューで誰かが気づく必要ではなく、ビルドが赤くなるからです。 さらに2本の規則で application を adapter から引き離し、層の順序を一方向に固定しています。

書いておいて一番よかった規則

受け入れテストには、動いているシステムへの継ぎ目が要ります。時計を進めるとか、データを仕込むとか。 その継ぎ目は裏口で、裏口は出荷されます。

java classes().that().haveSimpleNameStartingWith("TestSupport") .should().beAnnotatedWith(Profile.class)

テスト支援のクラスは Spring のプロファイルで隔離されていなければならない。3行です。 これで「なぜこのエンドポイントが本番に入っているのか」という事故が丸ごと一種類消えます。

最後の防衛線はデータベース

二重予約は並行性の問題で、アプリケーション層のチェックでは解けません。2つのリクエストが どちらも書き込む前にチェックを通過しうるからです。実際の保証は、部屋と時間帯に掛けた PostgreSQL の EXCLUDE 制約です。

面白いのは検証の仕方です。テストはアプリケーション層のチェックを意図的に迂回して リポジトリのポートへ直接書き込みます。証明したいのが制約単体の働きだからです。

L3（DB境界）: ダブルブッキングの最終防衛＝PostgreSQLのEXCLUDE制約の検証。 事前チェック（application）を通さずポートに直接保存し、DB制約だけで拒否されることを確かめる。

実行先は Testcontainers の実PostgreSQLで、インメモリの代用品ではありません。 H2で代用していたら重なりをそのまま受け入れ、保証が存在しないままテストは通っていたはずです。 境界で接するだけの隣接予約は許可されることも検証しています。時間帯のoff-by-oneはそこに住むからです。

実装より先に契約

OpenAPI文書が真実の源であって、後から書いた説明ではありません。フロントエンド側はそこから API型を生成しているので、クライアントがビルドに気づかれずに契約からずれることがありません。

受け入れシナリオは、それを満たすコードより先にmainへ入れられます。 @pending-implementation を付けて既定の実行から外す仕組みです。

些細に見えて、そうではありません。「何が正しいか」を、それ自体レビュー可能な変更として 合意しマージできるということです。答えを既に前提した実装と融合した状態で届くのではなく。

受け入れテストは専用のGradle source setに置き、step定義とアサーションの間にDSL層を挟んでいます。 シナリオがHTTP呼び出しではなくドメインの言葉で読めるようにするためです。

これが示していないこと

学習用なので、限界を正直に書いておきます。

デプロイはなく、認証もなく、テストが生む以上の負荷もかかっておらず、運用履歴もありません。 実際の利用の下で保守されたことも、実ユーザーの圧力の下で変更されたこともありません。 並行性の保証はDBレベルでは証明していますが、本物の競合に遭ったことはありません。

ここから持ち帰るものは「予約システムが作れる」より狭く、そして有用です—— テストが強制する境界は真実であり続け、図が説明するだけの境界はそうならない。
