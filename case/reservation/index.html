  • キャンセルはどう記録するのか

どれも「実装しやすい形にするために先に方向を決めておく」種類の問いです。 フィジビリティ検証は私の担当でしたが、そこまで見通せていませんでした。 結果として、他のメンバーがDBをモデリングする過程で洗い出してもらう形になりました。

正直に書くと、あの時点の自分に妥当なモデリングができたとは思っていません。 他人の設計が自分の見落としを炙り出した、というのが起きたことです。

このページは、そのうち2つに答えた記録です。3つ目には答えていません。

キャンセルはどう記録するのか

キャンセルされた予約は、誰かがセットした「キャンセル状態」にあるのではありません。 ある時点で何かが起きたのであって、状態はそこから導く結論です。

だから保存するのは cancelledAt だけ。状態は導出し、導出は1箇所にしか置きません。

java /** cancelledAt の有無から状態を導出する唯一の場所。 */ public static ReservationStatus of(LocalDateTime cancelledAt) { return cancelledAt == null ? CONFIRMED : CANCELLED; }

コードより重要なのはクラスのドキュメントに書いた規則です—— 他のどのクラスも cancelledAt を直接見て「キャンセル済みか」を判定してはならない。

同じ問いに真実の源が2つあると、状態モデルはそこから腐ります。ある呼び出し側はタイムスタンプを見て、 別の側は列挙を見て、いずれ食い違う。「状態を持つか、事実を持つか」を先に決めておけば、 DB設計の段階で議論する必要はありませんでした。

予約の重複はどう守るのか

これは並行性の問題で、アプリケーション層のチェックでは解けません。 2つのリクエストがどちらも書き込む前にチェックを通過しうるからです。 実際の保証は、部屋と時間帯に掛けた PostgreSQL の EXCLUDE 制約です。

面白いのは検証の仕方です。テストはアプリケーション層のチェックを意図的に迂回して リポジトリのポートへ直接書き込みます。証明したいのが制約単体の働きだからです。

L3（DB境界）: ダブルブッキングの最終防衛＝PostgreSQLのEXCLUDE制約の検証。 事前チェック（application）を通さずポートに直接保存し、DB制約だけで拒否されることを確かめる。

実行先は Testcontainers の実PostgreSQLで、インメモリの代用品ではありません。 H2で代用していたら重なりをそのまま受け入れ、保証が存在しないままテストは通っていたはずです。 境界で接するだけの隣接予約は許可されることも検証しています。時間帯のoff-by-oneはそこに住むからです。

実務で決められなかったことを、決める仕組みにした

問い自体より、なぜ決められなかったかの方が尾を引きました。

当時の私は技術選定と環境構築も主導していました。Vue 3・Tailwind CSS・C#/.NET という選定の決め手は 「社内に馴染みがある」で、それ以外の根拠を持っていませんでした。 そして決めた時点では、根拠が無いことに気づいていませんでした。

問題は選定そのものより、判断が妥当だったかを後から検証できないことです。 認証も同じで、Azure との SSO の経験が無いまま JWT で認証して保存する形にしました。 他の方式を検討していないので、それが妥当だったのか今も言えません。

いま使っているテンプレートが持っている規程は、ここから来ています。

当時起きたこと いま規程になっていること
選定の根拠が「馴染みがある」だけだった 選定は軸で比較し、ADRに残す
層の分離をAPI境界だけに頼った 依存方向をArchUnitで機械強制する
決めるべきことが実装段階まで残った 契約を先に承認し、実装より先にmainへ入れられる
認証方式を比較せずに決めた 案を並べて選び、採用しなかった案も記録する

層の境界は「合意」ではなく「強制」する

実務ではDDDを使えず、APIで分離するところまでしかいきませんでした。 API境界は物理的な分離であって、内側の構造は何も保証しません。

ヘキサゴナルの層は、描くのは簡単で破るのも簡単です。誰かがドメインオブジェクトの中に リポジトリを必要として、importを1行足す。それで図は静かに真実でなくなります。

だから方向をテストにしました。ArchitectureTest は、ドメインがフレームワークを 知った時点でビルドを落とします。

java noClasses().that().resideInAPackage("reservation.domain..") .should().dependOnClassesThat().resideInAnyPackage( "reservation.application..", "reservation.adapter..", "org.springframework..", "jakarta..", "javax..");

ドメインパッケージは現在 Spring も JPA も1つもimportしていません。その状態が保たれるのは、 破るとレビューで誰かが気づく必要ではなく、ビルドが赤くなるからです。

書いておいて一番よかった規則

受け入れテストには、動いているシステムへの継ぎ目が要ります。時計を進めるとか、データを仕込むとか。 その継ぎ目は裏口で、裏口は出荷されます。

java classes().that().haveSimpleNameStartingWith("TestSupport") .should().beAnnotatedWith(Profile.class)

テスト支援のクラスは Spring のプロファイルで隔離されていなければならない。3行です。 これで「なぜこのエンドポイントが本番に入っているのか」という事故が丸ごと一種類消えます。

実装より先に契約

実務ではモックを作りましたが、Viewと分離できておらず、本実装へ流用するのに手間がかかりました。 モックが「捨てるもの」でも「育てるもの」でもない中途半端な位置にいたからです。

ここではOpenAPI文書を真実の源にしました。フロントエンド側はそこからAPI型を生成しているので、 クライアントがビルドに気づかれずに契約からずれることがありません。 フロントエンド側はエンドポイントごとにモックと実バックエンドを個別に切り替えられ、 モックは捨てずに契約の別実装として残ります。

受け入れシナリオは、それを満たすコードより先にmainへ入れられます。 @pending-implementation を付けて既定の実行から外す仕組みです。 「何が正しいか」を、それ自体レビュー可能な変更として合意しマージできる—— 実務で実装段階まで残ってしまった判断を、前倒しするための仕掛けです。

これが示していないこと

デプロイはなく、認証もなく、テストが生む以上の負荷もかかっておらず、運用履歴もありません。 実際の利用の下で保守されたことも、実ユーザーの圧力の下で変更されたこともありません。 並行性の保証はDBレベルでは証明していますが、本物の競合に遭ったことはありません。 入退室履歴の問いには、前述のとおり答えていません。

本番で動いているのは実務の側で、こちらはその振り返りです。順序を逆にして読まれると困ります。

持ち帰ったものは「予約システムが作れる」より狭く、そして有用でした—— テストが強制する境界は真実であり続け、図が説明するだけの境界はそうならない。 そして決められなかったことは、決める仕組みが無かったから決められなかった。
