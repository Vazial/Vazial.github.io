規程が破れ、その規程が破れを捕まえた

開発中の摩擦——AIが迷った、間違った方向へ行った、指示が曖昧で事故った——は、 その場で書き留める規程になっています。原則としては正しく、そして実際には全部は書かれません。 だからセッションログを走査して読む価値のある瞬間を拾い、候補として戻します。 このループが最初に浮かび上がらせたのは、自分が作った規程が4回目に破れていたことでした。

ソース · 4つの台帳に friction 64件 · 決定は ADR-0049 と ADR-0055

なぜ書き留めるのか

friction の1件はバグ報告ではありません。何が起きたか、なぜかの仮説、そして 手間に見合う理由になる部分——修正をどの段へ押し込んだかを記録します。

同じ原因が繰り返したら、それは運が悪いのではなく規程の構造的欠陥として扱い、 修正は「次から気をつける」ではなく規程そのものの変更になります。

これは記録が存在して初めて機能します。その場で書くのは正しい——後からの再構成は細部を失うので。 ただし「書かなかった分は永久に失われてよい」までは意図していませんでした。 そして台帳には目に見える穴がありました。

素朴に数えると必ず間違える3つの癖

走査の前に、ログを正規化する必要がありました。そのまま測ると、自信に満ちた出鱈目が出るからです。 実測して畳んだのは3つです。

癖 実測 なぜ効くか
セッションがフォーク・再開する 全レコードの2割超が重複 分岐の多い週だけ分母が膨らみ、偽のトレンドが出る
役割agentは別ファイルに書く 108実行・メインとほぼ同量 委譲した先で起きた摩擦がメインの記録から見えない
role: user は人間とは限らない 通知231件 対 人間の発話522件 ツールの実行結果を人間の発話として数える

3つ目が一番効きます。役割agentのログでの role: user はorchestratorがそのagentへ渡した ブリーフです。素朴に数えると 私がagentへ出した指示 が 人間による訂正 に化ける—— 意味がほぼ反転します。捕まえる前に一度これが起きました。

正規化は1箇所だけで行い、その上の道具はすべて生ログではなくこの索引を読みます。 全再構築が約2秒なので、差分更新せずに毎回作り直しています。

読んでいるだけでは見えなかったもの

メインのトランスクリプトではなく正規化済みの索引の上で走らせた途端、 それまで一度も見えていなかったものが2つ出ました。

  • 同じエラーで23回連続して詰まっていたagent — architect が作業ディレクトリの誤りで、 誰も見ていない委譲実行の中で何度も何度も。
  • 無言の手戻り — orchestrator が役割agentに 「前回の私の指示が間違っていました」 と伝えて やり直させていた。本物の摩擦なのに未記録。外から見るとスライスが少し長引いただけだからです。

そしてセッションの中ではなく、跨いで見ると:

File does not exist … working directory が 14セッション・124回発生していて、 51件の台帳に1件も記録されていなかった。

1セッションの中では「エラーが何回か出た」にしか見えません。横断で見て初めて欠陥になります。

破れた規程

このループの名前の由来になった1件です。人間から、ADRが読みにくいと指摘されました—— 1枚だけ読んでも何のことか分からない、文章が硬い、と。

好みの議論をする代わりに、対象の49本を測りました。

ADR-0001〜0021 ADR-0022〜0052
本文に占める太字の割合 6.3% 15.5%
1本あたりの挿入節 0.7回 4.8回

原因は不注意ではありませんでした。人間が承認する成果物は冒頭に承認者向けサマリを持つ、 という規程は既にありました。ただしそれを作ったとき、例外の表がADRを 充足済み と判定していた—— 決定節が結論として機能しているから、という理由で。その判定が静かに真でなくなっていたのです。

これは同じ原因キーの4回目で、先行する3回は別プロジェクトの台帳に載っていました。 再発が見えたのは、4つの台帳が原因キーを共有しているからです。

修正は規程に入りました。ADRは自己完結で書く。そして機械が数えられる3項目—— 太字率・最長文長・挿入節の数——はlinterが報告します。

いつ走るか、なぜマージ時ではないか

走査はプルリクエストを作成する直前で、マージ後ではありません。

振り返りは仕事の終わりにやるものであり、PRの作成はこのワークフローでスライスを意図的に閉じて まとめる唯一の儀式だからです。

マージが不適な理由はもっと即物的です。マージ後に摩擦を記録するには2本目のPRが要る—— そして「記録するのに2本目のPRが要る」は、台帳で最も多く再発している項目そのものです。 収穫の仕組みが、自ら捕まえようとしている摩擦を生んでしまう。

実測もそう言っていました。gh pr create は30日で98回、gh pr merge は1日で12回。 マージは主にWeb画面で行われ、ローカルのhookからは見えません。

できないこと

正直な限界で、努力では消えません。

当然の問いは「このループで良くなったのか」ですが、仕事の流量が小さすぎて答えられません。 訂正率——前の指示を打ち直した人間の発話の割合——は現状およそ3.8%、週あたり約75プロンプトです。 これが半減したことを確信をもって検出するには、比較の片側に約1,200プロンプト必要で、 問いに答えられるようになるまで7か月半ほどかかります。

だから道具は改善を主張しません。「まだ判定できない」と言い、あと何件必要かを示します。 この流量で検出できるのは大きな悪化——およそ倍化なら約3か月——だけです。

測ったからといって、それについて結論を出す資格が生まれるわけではありません。 そうであるかのように見せるダッシュボードは、ダッシュボードが無いより悪い。 ここでの出力は人間が読むための候補であって、判定ではありません。
