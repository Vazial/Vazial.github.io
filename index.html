I build the method, then measure whether I follow it

When implementation is delegated to AI agents, reading the output to check it stops working the moment there is any volume. So I put the guarantee of correctness in mechanised verification instead, narrowed human involvement to four approval points, and then — because a method nobody checks is just an opinion — wired the operating logs back in to measure whether the method is actually being followed.

The template is the work. The projects below exist to put it under load.

The bet

Reviewing AI output by hand does not scale, and it fails quietly: the reviewer gets tired before the code gets correct. The alternative is to decide what "correct" means up front, encode it as executable contracts, and let CI be the thing that says no.

A person still approves four things, because these cannot be delegated to a machine: the contract (what correct means), the design skeleton (expensive to reverse), the step definitions (the mapping between prose scenarios and code), and changes to the rules themselves (a rule change cannot be self-certified).

Everything else moves into five verification levels, from unit tests up to experience quality, with failures caught at the level closest to the machine.

The rules live in the repository rather than here, because a portfolio page that restates them would drift away from them: ai-driven-dev-template.

What that produced

Over 2026-05-30 to 2026-08-23, across 5 projects: 401 commits, 196 pull requests, and 839 prompts actually typed by a person. Machine verification passed 98.0% of 493 runs — and, more usefully, failed the rest.

Where to look

Work → Four projects, each labelled with what it actually is — one running service, one heavily iterated build, and two study exercises. The labels matter more than the count.

Case: a design procedure in Java → A meeting-room booking domain worked through EventStorming, aggregate boundaries and concurrency, then carried into Java 21 and Spring Boot with the layer boundaries enforced by tests rather than by convention. Built to practise the procedure, not to operate.

Case: a loop that catches my own drift → Development friction is supposed to be logged as it happens. It isn't, reliably. So the session logs get scanned for the moments where things went wrong, and the results are handed back for review. The first thing it caught was a rule of mine breaking for the fourth time.
