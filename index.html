バックエンドエンジニア

方法論を作り、守れているかを測る

実装をAIエージェントに任せる開発では、出力を人間が読んで確かめる運用は量が増えた瞬間に破綻します。 だから正しさの保証を機械化された検証に移し、人間の関与を4つの承認点に絞りました。 そのうえで——誰も点検しない方法論はただの意見なので——運用ログを引き戻して、 その方法論が実際に守られているかを測っています。

テンプレートが本体です。以下のプロジェクトは、それに負荷をかけるために存在します。

何に賭けているか

AIの出力を人間がレビューして確かめる運用は、規模に対して伸びません。しかも壊れ方が静かです—— コードが正しくなる前に、読む側が先に疲れます。

だから「何が正しいか」を先に決め、実行可能な契約として書き、否と言う役目をCIに持たせます。

人間が承認するのは4点だけです。機械に委ねられないものだからです。

承認するもの なぜ人間か
契約（受け入れシナリオ・API仕様・ADR） 「何が正しいか」は機械に決められない
設計骨格 後から覆すコストが高い
step実装 散文のシナリオとコードの対応は機械検証できない
規程変更 ルール自体の変更は自己申告にできない

残りは5段の検証（単体テストから体験の質まで）に移し、失敗はできるだけ機械に近い段で捕まえます。

規程そのものはリポジトリにあります。ここで書き直すと必ず食い違うので、書き直しません: ai-driven-dev-template。

どこを見るか

仕事 → 4つのプロジェクトを、それぞれが実際に何であるかのラベル付きで。稼働中のサービスが1つ、 作り込み中が1つ、学習用が2つ。数より、このラベルのほうが重要です。

ケース: Javaでの設計手順 → 会議室予約のドメインを EventStorming・集約境界・並行制御から Java 21 と Spring Boot へ。 層の境界は規約ではなくテストが強制しています。手順を練習するために作ったもので、運用はしません。

ケース: 自分のずれを捕まえるループ → 開発中の摩擦はその場で記録する規程ですが、実際には書き落とします。だからセッションログを走査して 候補を拾い直します。最初に捕まえたのは、自分が作った規程が4回目に破れていたことでした。
