バックエンドエンジニア

方法論を作り、守れているかを測る

実装をAIエージェントに任せる開発では、出力を人間が読んで確かめる運用は量が増えた瞬間に破綻します。 だから正しさの保証を機械化された検証に移し、人間の関与を4つの承認点に絞りました。 そのうえで——誰も点検しない方法論はただの意見なので——運用ログを引き戻して、 その方法論が実際に守られているかを測っています。

きっかけは実務です。 7人のチームの初期メンバーとして予約・受付システムを作り、 自分が決めきれなかったことが後工程で表に出ました。以降の仕事は全部、 そこで決められなかったことを決められるようにするためのものです。

何に賭けているか

AIの出力を人間がレビューして確かめる運用は、規模に対して伸びません。しかも壊れ方が静かです—— コードが正しくなる前に、読む側が先に疲れます。

だから「何が正しいか」を先に決め、実行可能な契約として書き、否と言う役目をCIに持たせます。

人間が承認するのは4点だけです。機械に委ねられないものだからです。

承認するもの なぜ人間か
契約（受け入れシナリオ・API仕様・ADR） 「何が正しいか」は機械に決められない
設計骨格 後から覆すコストが高い
step実装 散文のシナリオとコードの対応は機械検証できない
規程変更 ルール自体の変更は自己申告にできない

残りは5段の検証（単体テストから体験の質まで）に移し、失敗はできるだけ機械に近い段で捕まえます。

規程そのものはリポジトリにあります。ここで書き直すと必ず食い違うので、書き直しません: ai-driven-dev-template。

どこを見るか

仕事 → 本番稼働中の実務システムと、そこから作った個人プロジェクト4つ。それぞれが実際に何であるかの ラベル付きです。数より、このラベルのほうが重要です。

ケース: 答えられなかった問いに、答え直す → 実務でフィジビリティ検証を担当しながら潰しきれず、DB設計の段階で表に出た3つの問い—— キャンセルの記録、予約の重複、入退室履歴。そのうち2つを、同じ形のドメインを別の言語で 組み直して答え直しました。残る1つには答えていません。

ケース: 自分のずれを捕まえるループ → 開発中の摩擦はその場で記録する規程ですが、実際には書き落とします。だからセッションログを走査して 候補を拾い直します。最初に捕まえたのは、自分が作った規程が4回目に破れていたことでした。

私について

C#/.NET と Java でバックエンド開発をしています。実装もできる設計屋を目指していて、 これは最近の方向転換ではなく最初からの目標です。実装がストロングポイントだったことはありません。

やりたい領域はドメイン駆動設計。ただしコンテナ・IaC・AWS も同じくらい好きで、 このサイトを日次で組み直している仕組みも、半分はその興味で作っています。

出身は四年制の工業系で、理論より作ることに重心のある教育でした。C言語でのマイコン、 Javaのオブジェクト指向、電子・電気回路設計とはんだ付けから入り、後半は制御工学・生産管理・ ロボット。開発課題はモータドライバで、インバータ実装を手伝い、ベクトル制御について 書きました。

モータのベクトル制御からブラウザの予約画面まで、抽象度を上下できることが、 ここに並んでいる仕事の共通点です。
