Session Radar 稼働中

個人で作ったもののうち実際に動いているのはこれだけです。毎朝08:00（JST）にGitHub Actionsのスケジュールが 発火し、connpass APIからイベントを取得、リポジトリ内のYAMLに書いた興味条件で絞り込み、 Discordへ1通のダイジェストを届けます。画面も永続ストアも持たず、外部I/Oは取得と配信の2つだけ。 配信先は NotifierPort の背後にあるので差し替えられます。

2026-08-23に実運用へ入り、以降スケジュールは自力で発火し続けています。ADR 5本。 小さいのは意図的で、面白いのは、方法論の産物が生きた外部APIと接触しながら、 私が手を入れなくても動き続けているという点です。

Dining Radar 作り込み中

個人プロジェクトの中で最も手を入れたもので、方法論を一番すり減らしました—— ADR 26本、frictionログ 26件。決定1つにつき記録された失敗が1つ、という比率です。 限られた範囲から食事場所を探すDjangoのパイプライン。

まだ改善中で、デプロイしていません。ここでの価値は反復回数です。テンプレートがどこで 軋むかについて私が知っていることの大半は、このプロジェクトから来ています。実在の地名を 公開リポジトリから外した判断と、その後の発見——プロジェクト名を変えても、既に広がった先からは 名前が消えていなかった——も含みます。

会議室予約 — バックエンド 実務の振り返り

上の実務で答えられなかった問いを、同じ形のドメインを別の言語で組み直して答え直したもの。 EventStorming から集約境界・並行制御・状態のモデリングを経て、Java 21 と Spring Boot へ。 ADR 8本と Gherkin の受け入れシナリオ。

作り込んでおらず、運用する予定もありません。 本番で動いているのは実務の側で、 こちらはその事後分析です。ここで示せるのは製品ではなく技術実践—— ドメイン層はフレームワークのimportを1つも持たず、そのことをテストが強制しています。 二重予約はモックではなく実PostgreSQLの制約で検証しています。

3つの問いのうち2つに答え、1つ（入退室履歴）には答えていません。
