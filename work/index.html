Four projects, and what each one was for

These are not four products. They are four different shapes of problem, used to find out where the method holds and where it tears. Each is labelled with what it actually is, because a study exercise presented as a running service is worse than either.

All four live inside ai-driven-dev-template under projects/, alongside the rules they were built under.

The template itself

The language-agnostic foundation: eleven principles, five role agents with separated context, five verification levels, and 58 architecture decision records covering the governance itself. This is the piece worth reading first, and the only one I would call finished enough to reuse.

The two case studies both come out of it — the design procedure shows it applied to a domain, the feedback loop shows it correcting itself.

Session Radar Running

The only one of these that actually runs. Every morning at 08:00 JST a GitHub Actions schedule fires, pulls events from the connpass API, filters them against interest criteria held as YAML in the repository, and delivers a single digest to Discord. No screens, no persistent store; external I/O is limited to one fetch and one webhook, behind a NotifierPort so the delivery channel is replaceable.

It went into real operation on 2026-08-23 and the schedule has been firing on its own since. Five ADRs. It is small on purpose — the interesting part is that the method produced something that survives contact with a live external API and keeps running without me.

Dining Radar In progress

The most heavily worked project of the four, and the one that wore the method down hardest: 26 architecture decisions and 26 logged friction entries, which is roughly one recorded failure per decision. A Django pipeline for finding somewhere to eat within a bounded area.

Still being improved, and not deployed. Its value here is the iteration count. Most of what I know about where the template chafes came from this project, including the decision to strip a real place name out of a public repository — and the follow-up finding that renaming the project did not remove the name from everywhere it had already spread.

Meeting room booking — backend Study exercise

Built to practise domain-driven design end to end, from EventStorming through aggregate boundaries, concurrency control and state modelling, into Java 21 and Spring Boot. Eight ADRs plus acceptance scenarios in Gherkin.

Not built out, and not intended to be operated. What it demonstrates is engineering practice rather than a product: the domain layer holds zero framework imports and a test enforces that, double-booking is verified against a real PostgreSQL constraint rather than a mock, and the acceptance suite is separated from the implementation by a DSL layer.

Meeting room booking — frontend Study exercise

The companion to the above, and where the contract-first idea got its real test: the API types are generated from the OpenAPI document rather than hand-copied, so the frontend cannot silently drift from the contract. Each endpoint can be switched from mock to real backend independently, one operation at a time, which made it possible to close the loop on availability, booking and cancellation without a big-bang integration.

88 unit tests, 9 Playwright end-to-end scenarios, 9 ADRs.
